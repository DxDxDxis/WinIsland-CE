# 1.2.4beta 歌词与 QQ 通知修复验证

日期：2026-09-07。最终构建：`1.2.4beta-minimized-lyrics-20260907-r8`。

## 实际结论

最小化后**歌词正文、歌曲识别和播放控制已验证仍可用**；本机网易云 **3.1.39.205426** 没有发布有效 SMTC 时间轴，最小化后的**连续实时歌词同步仍受限制**。现在保留已核验歌词，明确静态显示，不把恢复窗口后的正常表现称为最小化同步成功。

QQ 已增加直接读取辅助功能消息列表/未读预览的后台路径，不再仅依赖 Windows 系统通知。最终成品的真实观察中，已收到一条 `QQ.exe / qq-preview-accessibility` 通知并完成可见展示和收回。此前 r4、r6 各约 5 分钟、2.5 分钟观察分别记录 14 条真实通知完成展示。它们不是合成测试。尚不能承诺 QQ 所有会话、所有版本、所有消息类型逐条无遗漏。

## 已确认原因与修改

1. **歌词与播放位置被混为一谈。** 本机 SMTC 歌曲、歌手、专辑、播放状态和控制有效，但 Position、Start/End/MinSeek/MaxSeek、LastUpdatedTime 均为零。官方 API 只返回播放器发布的属性，不会替客户端制造进度。
2. **原界面依赖歌词预览。** 没有进度时长期停在“未同步 + 第一行”，而第一行常是作词信息。新增网易云 MSAA/IAccessible2 当前高亮行补充，核对歌曲、歌手和独立服务歌词后才显示；没有把歌词行起点当作实际播放秒数。重复句不能定位唯一行时，诊断索引为 -1。
3. **最小化使本机客户端的辅助功能当前行冻结。** 可见窗口时实测连续更新；最小化后不能把缓存 DOM 当成实时数据。现在按当前歌曲/歌词文档保留最后核验行，显示“静态歌词”，设置状态说明同步暂不可用。真正换曲或歌词文档变化会清理旧行；窗口状态变化本身不会清空歌词或重启请求。
4. **同歌时间轴变化触发重复请求。** 去掉请求 identity 中的 duration，歌曲关联、请求 generation 和最新时间轴状态分离；只有新匹配证据表明确有录音差异时才重查。旧请求不能覆盖当前曲目。
5. **旧 SMTC 游标可被无限外推。** 按官方 LastUpdatedTime 语义和单调时钟校准；最长外推 15 秒，重复读取旧属性不能延长有效期。过期后退为静态；暂停/恢复、跳转、曲目变化、新时间轴重新校准。从未有过有效进度的全零会话不会从零开始计时。
6. **QQ 通知渠道覆盖不足。** Windows `wpndatabase.db` 不覆盖 QQ 自绘弹窗或不弹窗的内部消息；这台 QQ NT 没有相应桌面 QQ 系统通知记录。新增 WinEvent/UIA 弹窗监听，以及 MSAA/IAccessible2 新收到消息/未读预览监听。读取前建立历史 ID 基线，不在启动时重放聊天记录，不记录正文到诊断。
7. **通知在收回中更新时短暂/漏显。** 相同通知 ID 内容更新会从当前几何反向展开，重新给予完整展示时间。记录发现、解析、过滤、入队、请求展示、实际渲染可见、结束展示的关联链路，音乐更新不移除通知队列。

QQ 直接读取使用 Windows 公开辅助功能接口，没有注入 QQ、修改其安装文件、读取登录凭据或解密协议。当前已读到的未读摘要只代表 QQ 暴露的最新预览：极快连续消息可能被 QQ 自身合并；未加载到辅助功能树的会话和内容仍有覆盖限制。多源都报告同一消息且没有共享消息 ID 时，也不能宣称已在所有 QQ 版本验证完全去重。

## 接口与依赖

保留顺序：本地导入优先；自动模式为 **正确匹配缓存 → LRCLIB `/api/get` → 网易云搜索确定 ID + `/api/song/lyric` → `/api/song/lyric/v1` → LRCLIB `/api/search`**。不增加新歌词服务。

使用现有原生 WinHTTP/C++ WinRT JSON，网络、解析、窗口读取在工作线程执行。歌词源返回时间标签不是本机播放位置；HTTP 200 还要通过业务码、JSON/歌词解析、歌曲/歌手/版本/已知时长/专辑匹配。

微软、LRCLIB 官方源码、网易云服务实测与当前社区接口实现的可复查链接、访问日期和限制见 [最小化歌词接口核验](最小化歌词接口核验.md)。网易云这两个地址是可验证的服务接口，未找到官方公开稳定性承诺。没有找到受支持且可验证、可替第三方获取该客户端后台本地实时进度的独立接口；这是本次核验范围的结论，不是断言任何内部实现均不存在。

成品为 x64 C++20，静态链接 VC 运行库；不需要 Python、Node、Qt 或开发环境。测试脚本只用于开发验证，不是应用依赖。使用 Windows 自带 WinHTTP、WinRT、MSAA/UI Automation、winsqlite3 与图形组件。SMTC 最低 Windows 10 1809；进程音频回环不可用时保留原系统峰值降级。

## 回归与性能边界

- 原生回归 53 项通过，包含时间单位、暂停/恢复、跳转、旧时间轴拒绝、过期上限、过期后暂停不能复活游标、歌词格式/缓存/配置兼容性。
- 通知/同步回归 11 项通过：同歌进度恢复不重复 HTTP，收回中更新重新展示，弹窗样式 fixture 的独立监听、排队、展开音乐共存、报告隔离和不记录正文。
- 多来源回归 28 项全部通过，进程退出码 0；覆盖既定请求次序、唯一匹配、LRC/YRC、Plain、旧请求取消、无歌词、指定源、本地导入/清除、限流退避后同曲恢复。结果文件为 `tests/lyric-providers-final8/results.json`。这组使用受控 HTTP 和合成 SMTC，不是真实播放器同步证明。

本次约 88 秒真实最终成品观察：渲染提交平均 0.653 ms，P99 桶 2 ms，最大 12.12 ms；活动帧回调平均 16.689 ms，P99 桶 22 ms，最大 46.626 ms。稳定采样段 CPU 约 1.2%–1.7%（20 逻辑处理器归一化），工作集约 71–73 MB。辅助功能后台读取平均 114.9 ms、最大约 981 ms，仍是外部进程 COM 调用，不能承诺任何硬件下均及时。

逐帧界面没有 COM/网络/歌词解析；节点缓存、分批有界遍历和 WinEvent 脏标记降低空闲重复读取；轮询有兜底，节点/监听在退出时释放。日志事件有上限，资源采样每 5 秒，歌词呈现诊断每约 2 秒，不写聊天正文。活动帧回调不是 GPU 实际显示 FPS；没有直接测 GPU 使用率。88 秒不能证明长期无泄漏，Windows 10、其它 DPI、多显示器与低配置机器仍待实测。
